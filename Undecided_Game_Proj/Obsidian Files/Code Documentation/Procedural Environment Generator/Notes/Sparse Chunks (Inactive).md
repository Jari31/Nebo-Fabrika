Sparse chunks are based on an algorithm named [Sparse Voxel Octree](https://en.wikipedia.org/wiki/Sparse_voxel_octree). This algorithm allows for the efficient storage of voxels based on sparsity. Where if a node within the structure contains the density of 0.0, then the node is simply not registered within the structure, conserving memory. Alongside, the SVO algorithm "zooms" out of the node structure with each consecutive pass until it either hits the root, or the specified depth. This allows for LoD (Level of Detail) generation, where the further away the player is, the blockier the super chunk gets. 

The game features an SVO implementation that only *constructs*; it does not do *traversal*. This means that it can only do LoD generation. Furthermore, the amount of voxels that it generates within a chunk is scaled down based on how far the closest important entity (for example, a player) is.

This implementation is also **volatile**. Where the super chunk simply discards all of its data (aside from vertices, time, etc.) after it finishes mesh generation. "Why not do streaming?" you may ask. Because the game has to process multitudes of planets, in the hundreds to thousands, per frame. Streaming to and from the disk and/or RAM would kill performance.

**SVO chunks do not compute physics (with some [[Notes/SVO Physics and Modification exceptions|exceptional cases]]) and are only computed on the client.** While an exception is in effect, the super chunk is promoted to a *dense grid* until the SVO is constructed and ready to be displayed. The resolution, however, is lowered based on the distance to the player.
